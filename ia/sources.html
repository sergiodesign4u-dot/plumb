Block 2 is dropped, and the global component agrees

A US B2B company of 50 to 300 people has one to three warehouse connections. Search over a list of three is dead weight, and a field that returns everything it is given teaches the analyst that search here is pointless, which is a bad thing to teach in a product where search is the mechanism that closes R2.

This is agreement with the global bar rather than a deviation from it. Node 0.1 already says search is a persistent affordance over the registry, not a global find-anything. Sources were never in its scope, and this is where that becomes visible.

The third column, because the bank's three collapse into two

The bank wrote 3.1's columns by analogy with 4.1: name, reachability, last successful run. Read against node 0.4, two of those are the same fact. 0.4 refuses "Healthy" by name, so a reachable connection is expressed as the time it last answered; and an unreachable one reads "Source is down. Last run 07:40", which already carries a time. Reachability and last run are one column in both directions, and the third is free.

The third column is a block the bank did not have, so it is named out loud and entered into the bank with its tracing. It traces to the inbound barrier: the analyst is asked why a number is different, and when a source is down, the difference between answering one person and answering five before they ask is knowing which metrics are affected. It is a count and not a score, so design principle 2 is intact: no aggregate, no health percentage, nothing to interpret.

The vocabulary is the reader's, and that is what node 0.4 is for

The connection is the analyst's object and the card is the reader's, and they say the same words about the same failure. A product whose whole claim is that a number means one thing cannot have its infrastructure page describing a failure differently from the page the customer's customer reads.

02

What the row does, and what it never shows

The row opens the connection, which is node 3.2 with its fields filled in. That mirrors cluster 4 exactly: 4.4 is both "new" and "edit", and 3.2 is both "connect" and "the settings of a connection that exists". A row overflow menu was refused in the bank and stays refused here, so testing a connection lives on 3.2, where 3.3 and 3.4 already are.

No credential on this page, not even masked

The row carries the warehouse type and the database, never a user, a key or a role. A masked secret in a list is still a secret in a list, and this product's compliance argument is that the customer's material is not ours to hold more of than we must.

Removing a connection, and the count we can name

A connection carrying metrics cannot be removed. The confirmation says how many and what to do: repoint them to another source or delete them first. Blocking is the decision, because the alternative is a class of orphaned metric whose connection no longer exists, and that would need a state of its own on the card, invented to cover a case we chose to allow.

Here the number can be named, and the contrast with node 4.7 is exactly whose object it is

Metrics are ours: definitions, owners and bindings live in our Postgres, so "8 metrics use this connection" is a fact we hold. Readings are not: nothing about who opened a card is stored, which is why 4.7 can name a consequence and never a count. The two pages behave differently because the architecture differs, not because one of them is less careful.

03

3.5 was missing from the map, and it is not what it looks like

Discovered here and registered in the map. Cluster 4 had an empty state for its listing and cluster 3 did not, which was an omission rather than a decision: the same canonical component cannot have empty behaviour in one place and none in the other. It inherits MVP from 3.1.

It is a recovery state, not an onboarding one, and that changes what it says

The map routes a new workspace from 3.3, testing the connection, straight into 4.2. So nobody arrives here on a first run: the only way to see an empty sources list is to remove the last connection. And it is narrower still, because a connection carrying metrics cannot be removed, so 3.5 is reachable only when the registry is empty too.

Which is why the sentence it carries is not "connect your first source to get started" but a plain statement that nothing is connected and nothing can answer.

The structure is retained, as at 4.2: the header row at width, a ghost row with the field labels at 360. Same canonical behaviour, which is the whole point of a canonical component.

04

Filters, feeling and the responsive rule

Filters and facets: none, and the reason is stronger here than at 4.1: with one to three rows there is nothing to filter. Written rather than left blank, per the template. Sort by name, and there is no second sort.

Nothing from the emotional and social table lands on this page

Written rather than padded. Those mechanisms live on the card, on the owner field and on the registry count. This page is infrastructure, and inventing an emotional claim for it is exactly the move the base layer forbade.

One adjacent note, and it is not a mechanism. The state column is the earliest place an analyst can learn that a source is down, before the inbound arrives. That is a real reduction of the ambush described in the As-Is map, but nothing in the research measures it, so it is named as a possibility and not as support for a job.

Responsive. At 360: title with count, primary action, then rows of three lines. No horizontal scroll, the same rule as 4.1, because a sideways table hides the state column and the state column is why the row exists. At width: three columns, sort arrow on the first, primary action to the right of the title, column widths set by the state column.

SEO: noindex, no schema, no SEO text. Behind sign-in, and it names the customer's warehouses.
